形式化语义：术语、关系与实例

W3C将Ontology描述为特定领域、由用户群体共享的形式化词汇表，术语通过与其他术语的关系获得定义。OWL 2提供类、属性、个体和数据值，并与RDF文档互通；其语义可供推理器执行一致性、包含关系和实例检索等查询。[2]

原文1

企业业务层：语义与受控操作

Palantir把Ontology定义为组织的操作层：在已整合的数据集、虚拟表和模型之上，连接真实资产、订单或交易。除对象、属性与链接外，还纳入动作、函数和动态安全，因此不只是存储实体关系的图谱。[3]

原文1

模式定义与实例更新必须分开

Palantir的object type是实体/事件的模式定义，object是具体实例；link type与link也有相同区分。action type先配置，再供用户执行对象修改。新增业务实例不能直接推断为自动发明新的类型、关系或动作模型；自动辅助建模与模式演化能力仍需另查产品证据。[4]

原文1

业务语义层与图schema不是同一种本体

应分开形式化OWL/RDF公理、可操作的业务对象/动作层、带定义/别名的图schema，以及LLM辅助本体构建。Stardog已补核TBox与查询时推理机制；Neo4j规范仅映射选定RDFS/SHACL构造，不能写成完整OWL实现。[10][20]

海外 · 企业操作本体 / 官方技术文档

Palantir · Foundry Ontology

本体定义

连接组织已整合数字资产与真实业务对象的操作层，兼具对象/属性/链接等语义元素和动作/函数/动态安全等操作元素。[3]

实现方式

将已有数据源映射为对象、属性与链接；用action types定义受控变更与决策流程，用functions承载业务逻辑。类型/属性/关系/动作定义与具体实例分别建模，动作类型配置后才被执行。[3][4] 已补核Pilot的提示驱动Ontology builder，可生成对象/链接/动作类型并对话精炼；在隔离工作区以种子数据测试，生产部署需分支推广、CI及发布步骤。该能力属于设计/开发辅助，不是每新增业务行即自行扩大业务模式。[9]

应用与Agent关系

官方描述支持资产、设备、产品、客户订单和金融交易等现实对象，并通过动作连接既有系统与决策流程。本轮尚未核验具体Agent或医药客户部署案例，不把操作能力自动等同于已落地Agent应用。[3]

证据与边界

官方Pilot公告首次为2026-03-05，文中更新注明10月26日当周GA，列回溯基线。现有证据支持AI辅助类型设计，但不支持“每个新业务实例自动发明新类型/关系/动作并完整提炼流程”的一般结论；Ontology SQL本身也不提供模式或数据写操作。[3][4][9][8]

Stardog · 语义层与Voicebox for Designer

本体定义

百度智能云 · 百度胜算 DataBuilder

本体定义

本体是底层数据到客户、订单等业务对象的标准化语义抽象；Object Type描述结构/属性/主键，Object是具体实例，Link Type是关联模板，Action Type封装业务操作。Data Agent可以用本体，但本体并非其强制前置依赖。[15]

实现方式

Object Type可无数据源创建权限表，或用现有元数据SQL创建虚表；SQL解析结构并按覆盖策略回填属性，可视化和DDL双向同步。定义需设置主键、属性和位置，发布到运行环境；Link Type也需发布。Action Type需先配置REST源、Webhook及参数映射，保存后另行发布；不是Agent自由发明动作。[16][17]

应用与Agent关系

Data Agent使用已授权数据集、对象类型、函数、数据搜索等上下文开展查询/计算。官网描述供应链打通ERP/MES/PLM与风险/替代料分析，属于厂商场景方案，未核实具名客户指标或医药部署。[15][18]

证据与边界

Object Type指南的2026-11-11是文档更新时间；没有历史版本差异证据，不能将全部能力称为当日新发布。版本、租户、部署形态和权限决定实际开放范围。数据回写Webhook动作不可撤销；Webhook升级不会使已有Action自动切换版本。[16][17]

Neo4j · Ontology Graph Specification / Context Engine

本体定义

Ontology Graph Specification用JSON/YAML描述节点、关系、属性、定义、别名、关系端基数和约束，并有外部标准引用。Context Engine另以六层业务本体连接业务流程/领域、数据产品/物理系统/工具集成、运行时知识。不能仅由图数据库身份推定已有这些本体能力。[20][19]

实现方式

规范按发布的JSON Schema校验，使用稳定ID与语义版本，扩展字段承载数据源映射等工具事项；仅声明对选定RDFS/SHACL构造的映射，未定义RDF序列化。Context Engine由企业定义并存储本体，Context Studio管理治理，Context Build/Runtime接入数据与GraphRAG，Memory/Learning记录决策路径。[20][19]

应用与Agent关系

海外 · 产品 / 可执行业务语义与决策建模 · 建档回补

RelationalAI · PyRel语义模型

本体定义

PyRel的Model是业务语义地图，显式描述概念、属性、关系与数据来源，以共同业务含义支持人和Agent推理。厂商将本体核心概括为概念身份、关系和约束；不能因此认定实现等同完整OWL语义。[24][23]

实现方式

在schema.py定义Concept、标识属性、Property和Relationship，source.py分别定义数据行到基础事实的映射；编译并部署为Snowflake视图、表、过程、任务，集中提供业务逻辑。分离模型含义和事实来源后，可调整数据来源而不必重写全部语义。[24]

应用与Agent关系

官方供应链教学模型判断供应商中断影响哪些产品；部署输出可通过SQL/PyRel消费，并以语义视图接入Snowflake Cortex Agent。属于可核实现路线，不把教程样例和首页演示金额当客户真实效果。[24][25]

证据与边界

OSI扩展文章首次为2026-05-29，作历史语义基线；标准讨论不代表所有供应商已实现兼容。具体模式变更审批、实例刷新时延、完整Agent权限继承和医药客户生产效果本轮未全面核验。

NVIDIA · Auto Ontology

本体定义

官方开源库从企业元数据建立上下文层，组织业务Terms、受审SQL attributes和连接Relationships，并与已有语义模型互补。Postgres/pgvector是目录、本体和嵌入存储，不是将向量库自身称为本体。[26]

实现方式

目录摄入读取表/列/键/视图/查询历史；SQL抽样加LLM建议外键、术语和描述，跨表规则、模型与数据连接验证形成语义关系。管理员开启语义编译后按启动、周期及按需运行；新编译主要处理尚无term的表，保留人工编辑，并可导入/导出Ossie YAML。回答经检索、确定性连接路径、LLM SQL、静态/模型校验与修复。[27]

应用与Agent关系

MCP提供readiness、术语查询、answerability和问答只读工具，另有CLI/API。官方Wide World Importers教学流程返回SQL与步骤，不是生产客户效果；Vietnamese Legal Ontology论文只借鉴五阶段设计、明确未部署NVIDIA服务，不能当该产品客户案例。[26][27]

证据与边界

本轮未核明首次发布日期，列建档基线。重要限制：认证只标记已审核，不改变Agent检索策略；每次编译重新选择默认语义外键，关闭选择不持久；Chat不自动调用check_answerable。部分校验/PII检测默认关闭，后端与摄入端需私网保护。未独立运行或核验准确率。

AutoOntic: Automatic Ontology Induction from Text for Knowledge Graph Construction

针对无schema抽取产生扁平图的问题，AutoOntic依次抽取带类型三元组、归一关系/类型、诱导单父类型层次、受层次约束地合并实体并归纳domain/range。层次插入以语料关系分布排序，再由局部LLM父子判断调整已有链接。作者在MINE-1报告无预设本体的信息保留率85.87%，加入Wikidata种子后88.00%；不是一般业务准确率。[30][31]

适合把跨文档抽取升级为可检查类型层次，也直接提供“自动模式构建”研究证据，但不是Palantir的通用自动业务流程产品。局限：单父层次、英语语料；参考类型相近不等于抽取事实正确，更粗domain/range也可能让指标变好。[31]

OGDA: Ontology-Grounded Data Agents for Reliable Analysis over Heterogeneous Data Lakes

OGDA用proposer提出字段schema、概念与关系，再由verifier对原始数据做假设检验；执行时先通过紧凑本体找数据，只有观察了数据语义才允许扩展任务图和处理动作。在KramaBench与DiscoveryBench、三种模型下，作者报告相对最强基线的KramaBench答案分最高提高10.82个百分点；流程覆盖分并非全面最佳。[33][34]

可用于企业多表数据湖的受控分析，关键不只是检索，而是把数据含义验证与任务图准入结合。验证只对当前湖数据成立，脏数据仍会形成一致但错误的语义；不覆盖图像/音频等无记录字段模态，也不承诺正式OWL推理。[34]

From Fluent Text to Ontology-Compatible Definitions: A Quality-Control Agentic Workflow

将生物医学定义生成改为质量控制流程：生成定义→抽取关系公理→对目标本体查谓词/对象→ROBOT模板与推理器检查→针对不存在实体或逻辑不一致分别修复。研究提出EER与LIR，在Disease Ontology、Uberon及约束压力集评估。作者发现存在性修复能降低实体错误，但逻辑冲突修复仍有限，文本相似度高也不保证能合并入本体。[36][37]

CLADE: Category-Level Answering from Deficient Evidence in Retrieval-Augmented Language Models

CLADE区分“完全无信息”和“只给疾病家族”的不足证据；用PrimeKG/MONDO药物—疾病问题及GloBI复现模型在家族线索下更少拒答、仍易猜错。正确家族已知时本体候选列表覆盖抽样答案98.5%，但自动找到目标家族是瓶颈；模型选家族的端到端恢复为26.8%，不是98.5%。[41][42]

Bag of concepts can enhance other text representations for medical systematic review screening

研究把本体概念袋BoC与BoW、PubMedBERT、Jina及LLM嵌入结合，在医学系统综述筛选中用随机森林、聚类初始化和不确定性采样逐批请求专家标注。比较不同术语库/MedCAT配置，以95%召回下的工作量节省及性能曲线衡量。作者在DERP案例中报告融合特征平均更好，Qwen3+BoC平均最佳，但各题目效果不同。[43][44]

HeriKGQA: Grounded Knowledge-Graph Question Answering over Cultural Heritage Sensor Data

HeriKGQA将SOSA/SSN与CIDOC-CRM对齐为遗产传感器本体，Ontop把SPARQL映射到SQL。LLM只解析受schema约束的JSON意图和表述答案；统计、时空和异常判断由查询与代码算，空数据不能算作0。作者在五站点500模板问题上报告99.0%准确率；相对最强基线18.2点优势中12.2点由grounding消融支持。[45][46]

OntoChat: a Framework for Conversational Ontology Engineering using Language Models

OntoChat以对话共同拟定用户故事，抽取/拆分能力问题，再去重聚类并将OWL本体文字化作问题覆盖测试。论文通过音乐本体重建、领域专家与本体工程师反馈及正负能力问题评估；作者报告56个问题的覆盖分类准确率87.5%，不是形式化推理正确性。[57][58]
